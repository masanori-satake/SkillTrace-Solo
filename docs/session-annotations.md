# セッション注釈 JSONL 仕様 v0.4（ドラフト）

状態: 下書き。2026-11-11 の設計議論から起こした。1.14.0 で SkillTrace-Solo が読み手として対応し（履歴の評価表示とセッションサマリの「注釈」節）、この文書を本リポジトリで管理する。書き手としての対応（SkillTrace からの評価・メモ入力）は後続の段階で行う。
改訂履歴: v0.1 初版。同日 v0.2 で、注釈ファイルの命名規則（プレフィックスと producer の使用可能文字）を追加した（§2.1）。同日 v0.3 で、値の型（`value_type`／`unit`／`label`）を追加した（§3.6）。同日 v0.4 で、フォルダ名を `.skilltrace-annotations` に決定した（§2）。
この仕様自体は特定のツールに属さない。対応する読み手・書き手は、この文書だけを根拠に実装できることを目指す。

## 1. 目的

AIエージェント（GitHub Copilot、Amazon Kiro 等）のセッションについて、**人の評価やメモを、元のセッション記録には一切手を入れずに**、外部ファイルへ追記できるようにするための共通形式。

- 元のセッション記録（各ツールのログ）は読み取り専用のままにする。
- 注釈はツール側のファイルに、セッション（またはその中のターン）を指して記録する。
- 記録形式を公開仕様とすることで、書き手（評価を入力する拡張機能・外部ツール）と読み手（表示・集計するツール）を独立に作れるようにする。
- 集計が機械的にできる形にしておくことで、スキル別・版別の「上手くいった率」のような二次利用を可能にする。

## 2. 置き場所とファイル構成

注釈は「フォルダに、書き手ごとの JSONL ファイルが並ぶ」形で保持する。

| 範囲 | 置き場所 | 性格 |
|---|---|---|
| 個人用（既定） | `~/.skilltrace-annotations/` | その人のマシン内だけ。ワークスペースを跨いで合流できる |
| 共有用 | `<ワークスペース>/.skilltrace-annotations/` | チーム共有。Git 管理されうる。書くのは利用者が選んだ場合のみ |

フォルダ名は `.skilltrace-annotations` とする。理由は所有の明示である。一般的な名前（例: `.skill-annotations`）では、何のツールに属するデータか分からず、そのツールを使わなくなったときに「消してよいものか」を判断できない。`skilltrace-` で始めることで、SkillTrace とその連携ツール群のデータであることが分かり、引退時の判断（消去してよい）もしやすくなる。形式自体は特定ツール専用ではないが、置き場所の名前空間は主たる読み手である SkillTrace のものを借りる、という割り切りである。

- フォルダ内はフラットに保つ。注釈ファイルの命名規則は §2.1 に従う。
  - 例: `ann-skilltrace-solo.jsonl`、`ann-skillbench.jsonl`、`ann-manual-notes.jsonl`
- **各書き手は自分のファイルにだけ追記する。他の書き手のファイルには触らない。**
  これにより、複数ツールの同時書き込みによる競合を構造的に避ける。
- 読み手は、個人用と（開いているワークスペースの）共有用の両フォルダにある注釈ファイルをすべて読み、対象ごとに束ねて統一的に表示する。表示の際は由来（個人／共有、書き手）が分かるようにする。
- ファイルが無い、フォルダが無いことは異常ではない（注釈ゼロとして扱う）。

### 2.1 注釈ファイルの命名規則

注釈ファイル名は次の形に固定する。

```
ann-<producer>.jsonl
```

- `ann-` は注釈ファイルを表す固定プレフィックス。
- `<producer>` は書き手ツールの識別子で、使用できる文字は次の正規表現に一致するものだけとする。

```
^[a-z0-9]+(-[a-z0-9]+)*$
```

  - 小文字の英字（a-z）と数字（0-9）のみ。区切りはハイフン `-` で、ハイフンは先頭・末尾・連続には使えない。
  - 大文字を使わないのは、Windows や macOS の大文字小文字を区別しないファイルシステムで、`ann-SkillTrace.jsonl` と `ann-skilltrace.jsonl` が同じファイルに化ける衝突を避けるため。
  - ドット、空白、アンダースコア、非 ASCII 文字は使わない（拡張子との混同、シェルや URL での扱い、並び順の環境差を避ける）。
  - レコード内の `producer` フィールド（§3.1）は、この `<producer>` と完全一致させる。
- 読み手は、フォルダ内のエントリ名が次の正規表現に一致するファイルだけを開く。**一致しないファイルは中身を見ずに素通りする**（判定は名前だけで完結し、高速にスキップできる）。

```
^ann-[a-z0-9]+(-[a-z0-9]+)*\.jsonl$
```

  - これにより、フォルダに `README.md`（人向けの説明）や一時ファイル、バックアップ（`ann-x.jsonl.bak` 等）があっても誤って読むことはない。フォルダ内に規格外のファイルが存在すること自体は禁止しない。
  - サブフォルダは走査対象外とする。

## 3. レコード形式

- 1 行 = 1 つの JSON オブジェクト（JSONL）。文字コードは UTF-8、改行は LF を推奨。
- 追記専用。**既存の行を書き手が書き換えたり削除したりしてはならない。** 修正は新しい行で行う（§6）。

### 3.1 必須フィールド

| フィールド | 型 | 意味 |
|---|---|---|
| `v` | 数値 | スキーマ版。この文書では `1` |
| `id` | 文字列 | 注釈の識別子。UUID を推奨。同じ注釈の改訂では同じ `id` を使う |
| `ts` | 文字列 | この行を書いた日時。ISO 8601（タイムゾーン付き） |
| `producer` | 文字列 | 書き手ツールの識別子。ファイル名の `ann-<producer>.jsonl` の `<producer>` 部分と一致させる（§2.1） |
| `target` | オブジェクト | 注釈の対象（§3.3） |
| `kind` | 文字列 | 注釈の種類（§3.4） |

### 3.2 任意フィールド

| フィールド | 型 | 意味 |
|---|---|---|
| `producer_version` | 文字列 | 書き手ツールの版 |
| `author` | 文字列 | 評価した人の識別子または表示名。集計を評価者別に行うために使う |
| `value` | 任意 | 注釈の値。`kind` が `verdict` のときは §3.4 の値。その他の `kind` では §3.6 の型情報とセットで使う |
| `value_type` | 文字列 | `value` の型（意味）。§3.6 の一覧から選ぶ |
| `unit` | 文字列 | `value_type` が `number` のときの単位（例: `tokens`、`credits`、`回`） |
| `label` | 文字列 | 値の表示名（例:「成功率」「手戻り回数」）。サマリ等が値の隣にそのまま出せる |
| `text` | 文字列 | `kind` が `note` のときの本文、その他の `kind` の補足メモ |
| `tags` | 文字列の配列 | 自由なタグ。理由の分類などに使う |
| `experiment` | オブジェクト | 比較実験との紐づけ（§3.5） |
| 上記以外の任意のフィールド | — | 書き手は独自フィールドを追加してよい。読み手は知らないフィールドを無視しなければならない |

### 3.3 target（対象）

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `source` | 文字列 | ○ | 記録源。`copilot-cli` / `copilot-vscode` / `kiro`（将来追加ありうる） |
| `session` | 文字列 | ○ | 対象セッションの ID（記録源が付けた ID をそのまま） |
| `turn` | 数値 | — | ターンを対象にする場合の、ターン通し番号（1 始まり） |
| `turn_ts` | 文字列 | — | 対象ターンの時刻（ISO 8601）。ターン番号の解釈が記録源の変更でずれた場合の照合用アンカー |
| `session_started` | 文字列 | — | セッション開始時刻。同 ID の取り違え防止の補助 |
| `workspace` | 文字列 | — | セッションが属するワークスペースのパスの控え（表示・照合用） |

- `turn` が無い注釈は、セッション全体への注釈とする。
- ターン番号は「読み手（サマリ表示）が数えるターンの通し番号」と定義する。記録源ごとに元の数え方が違う可能性は `turn_ts` で検出できるようにしておく。

### 3.4 kind（種類）と verdict の値

標準の `kind`:

| kind | 意味 | 使うフィールド |
|---|---|---|
| `verdict` | 対象の成否・出来の評価 | `value`（必須）、`tags`、`text` |
| `note` | 自由なメモ | `text`（必須） |
| `tag` | タグだけの付与 | `tags`（必須） |
| `retract` | 取り消し（§6） | — |

- `verdict` の `value` は **3 段階**: `good` / `ok` / `bad`。
- 独自の `kind` を定義する場合は `x-<producer>-<名前>` の形とし、標準の読み手は知らない `kind` を（内容を表示できない旨の注記つきで）無視または保持してよい。標準 `kind` の意味を独自に変えてはならない。

### 3.5 experiment（比較実験との紐づけ、任意）

比較ツールの実験セッションに付ける場合の例示フィールド。

```json
"experiment": {"id": "SKILL-123/run3", "ticket": "SKILL-123", "set": "B", "set_ref": "feature/skill-123@<commit>"}
```

読み手はこの情報があれば「実験のどのセットの実行か」を表示・集計に使える。無ければ通常のセッション注釈として扱う。

### 3.6 値の型（value_type）

注釈が値を持つ場合、その**意味（型）を値と一緒に記録する**。読み手は型を見て表示方法を決められる（数値なら数値らしい整形、割合なら % 表示など）。型は「意味」の宣言であり、具体的な見た目（桁数、色など）は読み手の UI が決める。

| value_type | value の形 | 意味と正規形 |
|---|---|---|
| `text` | 文字列 | そのまま表示する文字列 |
| `number` | 数値 | 数値。単位がある場合は `unit` を併記する |
| `percent` | 数値 | 割合。**正規形は 0〜1 の比率**（0.75 は 75% を意味する）。75 や `"75%"` のような形で書いてはならない（二重に % 化される事故を防ぐため） |
| `boolean` | 真偽値 | はい／いいえ |
| `duration` | 数値 | 所要時間。**正規形は秒**。表示側で分・時間への整形を行う |
| `enum` | 文字列 | その `kind` が定義する選択肢のうちの 1 つ（`verdict` の値はこの型） |
| `timestamp` | 文字列 | 時点（ISO 8601） |

規則:

- 標準 `kind`（`verdict`、`note`、`tag`）では、値の意味は §3.4 で定義済みのため `value_type` を省略してよい。
- **独自 `kind` で `value` を使う場合は、`value_type` の付与を必須とする。** 型の無い値は、読み手が表示も集計もできないため。
- 値には表示用に整形済みの文字列（`"75%"`、`"12,500"` 等）を入れてはならない。整形は読み手の仕事であり、正規形で記録する。
- 1 レコードの値は 1 つを原則とする。複数の指標を付けたい場合は、指標ごとにレコードを分ける（`label` で指標名を示す）。
- 読み手は、知らない `value_type` に出会ったら、値を整形せずそのまま（JSON のリテラルとして）表示すればよい。表示が最適でなくなるだけで、壊れてはならない。

表示の目安（参考であり、読み手の UI ポリシーが優先する）:

- `percent`: 小数第 1 位までの % 表示（例: 0.756 → 75.6%）
- `number`: 桁区切りを付ける。`unit` があれば後ろに添える
- `duration`: 60 秒未満は秒、以上は分秒または時間への整形
- `boolean`: 記号または短い語（例: ✓／−）

## 4. 例

セッション全体への評価:

```json
{"v":1,"id":"2f6d…","ts":"2026-11-11T12:05:00+09:00","producer":"skilltrace-solo","author":"satake","target":{"source":"copilot-cli","session":"f6c3148f-…"},"kind":"verdict","value":"good","tags":["steering遵守"],"text":"一発で意図どおりに直った"}
```

ターンへのメモ:

```json
{"v":1,"id":"7a91…","ts":"2026-11-11T12:07:30+09:00","producer":"skilltrace-solo","target":{"source":"kiro","session":"sess_6d82612c-…","turn":3,"turn_ts":"2026-11-11T11:58:02+09:00"},"kind":"note","text":"このターンから指示が逸れ始めた"}
```

実験セッションへの評価:

```json
{"v":1,"id":"b3c0…","ts":"2026-11-11T12:10:00+09:00","producer":"skillbench","target":{"source":"copilot-cli","session":"0be54d21-…"},"kind":"verdict","value":"bad","experiment":{"id":"SKILL-123/run3","ticket":"SKILL-123","set":"B"}}
```

型つきの値（外部ツールが付けた指標。読み手は `percent` を見て 75% と表示できる）:

```json
{"v":1,"id":"e41a…","ts":"2026-11-11T12:12:00+09:00","producer":"acceptance-checker","target":{"source":"kiro","session":"sess_6d82612c-…"},"kind":"x-acceptance-checker-pass-rate","label":"受け入れ確認の合格率","value":0.75,"value_type":"percent"}
{"v":1,"id":"e41b…","ts":"2026-11-11T12:12:00+09:00","producer":"acceptance-checker","target":{"source":"kiro","session":"sess_6d82612c-…"},"kind":"x-acceptance-checker-rework","label":"手戻り回数","value":2,"value_type":"number","unit":"回"}
```

## 5. 読み手の規則

1. すべての対象フォルダについて、§2.1 の命名規則に一致するファイルだけを開き、1 行ずつ解釈する。規則に一致しないエントリは開かずに素通りする。
2. **壊れた行（JSON として解釈できない、必須フィールド欠落）は、その行だけを飛ばし、読み込み全体を失敗させない。**
3. `v` が自分が対応する版より大きい行は飛ばす（可能なら件数を注記する）。
4. 知らないフィールド・知らない `kind` は無視する（§3.2、§3.4）。
5. 同じ `id` の行が複数ある場合は §6 の改訂解決を行う。
6. 表示ではテキストを必ずエスケープして扱う。**注釈は他ツールが書いた外部入力であり、HTML 等にそのまま埋め込んではならない。**
7. 個人用と共有用で同じ対象への注釈が両方にある場合は、どちらかを隠さず並べて表示し、由来を区別する。複数人の注釈も同様に「複数の見方」として並べ、勝手に1つに潰さない。
8. 値の表示は `value_type` に従って整形する（§3.6）。知らない `value_type` は整形せずそのまま表示する。`label` がある場合は値の表示名として使う。

## 6. 改訂と取り消し

追記専用のまま編集を表現するため、次の規則を用いる。

- **改訂**: 同じ `id` で新しい行を追記する。読み手は、同じ `id` の中では `ts` が最新の行を有効とする（`ts` が同値ならファイル内での後方の行）。
- **取り消し**: 同じ `id` で `kind: "retract"` の行を追記する。その注釈は無かったものとして扱う（集計からも除外する）。
- 改訂・取り消しは原則として、元の書き手（同じ producer のファイル内）でのみ行う。

## 7. 書き手の規則

1. 追記するのは、§2.1 の命名規則に従った自分の `ann-<producer>.jsonl` のみ。他者のファイル、対象セッションの記録ファイルには書き込まない。規則に一致しない名前の注釈ファイルを作ってはならない。
2. 1 行に 1 オブジェクトを完全な形で書く（整形出力しない）。追記の途中で他プロセスが読んでも、最後尾の不完全な行は読み手が §5-2 で跳ねる前提とする。
3. `id` は注釈ごとに新規に採番し、改訂時だけ再利用する。
4. 共有用フォルダへ書く場合は、内容が共有（Git 管理）されうることを利用者が分かる形にしてから書く。既定の書き込み先は個人用。
5. 独自 `kind` で `value` を書く場合は `value_type` を必ず付け、値は §3.6 の正規形で記録する（割合は 0〜1 の比率、時間は秒、整形済み文字列は不可）。

## 8. 集計（参考、仕様の本体ではない）

読み手・集計ツールの例:

- スキル別、スキルセットの版別に `verdict` を数え、`good` の割合（上手くいった率）を出す。`retract` 済みと改訂前の行は数えない。
- `experiment` つきの注釈だけを集めれば、比較実験の「質」の欄を印象ではなく実セッションの評価集計で埋められる。
- 評価者によって基準が違う可能性を考慮し、`author` 別の集計も可能にしておく。

## 9. セキュリティ・プライバシー上の注意

- 注釈の本文には業務情報や個人的なメモが入りうる。既定を個人用フォルダとしたのはこのため。
- 共有用に書かれた注釈は、リポジトリの閲覧権を持つ人に見える前提で扱う。
- 読み手は §5-6 のとおり、注釈テキストを信頼できない入力として扱うこと。

## 10. 版の進め方

- `v` は破壊的変更のときだけ上げる。任意フィールドの追加、標準 `kind` の追加は `v` を上げない（読み手が無視できるため）。
- この文書の版（v0.1、v0.2…）とレコードの `v` は別物。前者は文書の改訂履歴、後者はデータ形式の版。

## 11. 未定事項

- （解消）フォルダ名は `.skilltrace-annotations` に決定（§2）。
- 仕様と書き手・読み手の正式名称。
- `source` の値の追加手続き（新しい記録源が現れたとき）。
- サマリ（SkillTrace）への表示位置と、ライブ表示での入力UIの詳細。これは読み手側の実装事項として別途決める。
