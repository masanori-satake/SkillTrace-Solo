# 04. サマリの読み方 — 「どこに払っているか」を読む

## この文書で分かること

- SkillTrace のサマリに出てくる実測の数字を、どう読み解くか
- Copilot の「入力の3分解」（新規入力 / キャッシュ読取 / キャッシュ書込）が
  何を教えてくれるか
- 「キャッシュ書込が発生したターン」を観測として読む方法
- Kiro の「最初に記録された文脈使用率」が、常時文脈の重さを
  どう表すか

## 出発点: サマリの数字は全部「実測」

SkillTrace のサマリに並ぶ数字は、すべてセッション記録に残っていた
実測です。単価を掛けた換算値や、見積もりは混ざっていません
（ファイル単位の「推定トークン」だけは例外で、そう明示されます）。

では実測だけで何が分かるのか。この文書のテーマは、実測の
**構成比**から「このセッションは、どこに払ったのか」を読むことです。
消費の構造は、合計の数字だけでは見えません。

## Copilot: 入力の3分解を読む

Copilot の記録では、「入力」はキャッシュ分を含む総数です。
SkillTrace はこれを3つに分けて表示します。

| 区分 | 意味 | 性質 |
| --- | --- | --- |
| 新規入力 | そのターンで初めて送られた入力 | 会話の進行そのもの |
| キャッシュ読取 | 前のターンと共通する入力の再利用 | 安い。再利用が効いている証拠 |
| キャッシュ書込 | 将来の再利用のために保存された入力 | 高い。文脈をキャッシュに「載せる」コスト |

実例（基礎データの phase0-probe）では、入力 71,271 の内訳は
キャッシュ読取 52,862 / キャッシュ書込 18,397 / 新規入力わずか 12 でした。
つまり入力の 99.98% がキャッシュで、新しく送った内容はほぼ無かった。
小さなスキルを同一文脈で往復した、というセッションの姿が
構成比からそのまま読めます。

読み方のコツは2つです。

- **書込の比率が高いセッションは「載せる」ことに払っている**。
  キャッシュ書込は、公開されている単価体系ではキャッシュ読取より
  ずっと高く設定されています（02 参照）。ただし、比率の高さだけでは
  「何度も載せ直した」とは言えません。短いセッションでは、初回の
  初期載せだけで比率が高くなります。繰り返しの載せ直しかどうかは、
  次の「発生ターン」で見ます
- **読取の比率が高いセッションは「読み回し」で済んでいる**。
  一度載せた文脈が再利用され続けた姿です

## キャッシュ書込の発生ターンを読む

ターン別の表の下には「キャッシュ書込が発生したターン」が
観測として示されます。読み方はこうです。

- **初回ターンに集中している**: 正常な姿です。セッションの最初に
  文脈をキャッシュへ載せるコストが、ここに集まります
- **途中ターンで大きな書込が再び発生している**: 文脈が作り直された
  痕跡です。引き金になり得るのは、長時間の放置（キャッシュには
  有効期限があります）、モデルの切り替え、ツール構成の変更などです

大事なのは、これは**観測であって診断ではない**、という線引きです。
「ターン3で大きな書込が発生した」は記録に基づく事実ですが、
「なぜ起きたか」は記録だけでは決まりません。心当たり
（昼休みを挟んだ、モデルを変えた）と照らして読むための
手がかりとして置かれています。

SkillTrace がこの一文を出すのは、「書込は高い」という構造を
知っていると、セッションの思わぬ消費に早く気づけるからです。
たとえば、放置のたびに大きな書込が繰り返される使い方なら、
常時文脈を軽くする・セッションを区切る、といった対策が
検討できます。

## Kiro: 常時文脈の重さを読む

Kiro の実測はクレジットです。Kiro の消費を支配するのは、
そのセッションで**常時文脈がどれだけ重いか**です。

自宅環境の実測が対照的でした。最小構成のプローブ
（スキル1つを辿るだけ）の1ターンは 0.82 credits。
一方、12ルートのワークスペース（AGENTS.md と steering が大量に
常時読み込まれる環境）での1ターンは 19.88 credits。約24倍です。
2つのセッションは作業内容も異なるため、この比較だけで原因を
切り分けることはできませんが、差の主な要因は、会話の前に
読み込まれる文脈（常時文脈）の量の差と見られます。

それを見える形にしたのが、常時文脈の節に併記される
**最初に記録されたコンテキストウィンドウ使用率** です。
最初の `contextUsage` は、セッションの早い段階（最初のターンの
途中）で記録されます。プロンプトや、その前に読み込まれたファイルも
含まれるため、常時文脈だけの使用率がいくらかは分かりません。
それでも、セッション初期の水準として、常時文脈の重さを見る
手がかりにはなります（プローブでは 4.1247%）。

読み方:

- **最初の記録の使用率が高い環境では、すべてのターンが重くなる
  傾向があります**。常時文脈は毎ターンの入力に含まれ続けるためです。
  ターン別のクレジットと並べて見ると、「この環境では1ターンあたりの
  地代が高い」ことが分かります
- **常時文脈を軽くすることは、Kiro では効きやすい節約**です。
  steering の棚卸し（本当に常時読み込みが必要か、参照で足りないか）が、
  ターンごとのクレジットを下げる方向に効きます

## 両プラットフォーム共通の注意

- **単位は換算できません**。トークンとクレジットは土台が違うので、
  大小比較はできません（03 参照）。比較できるのは、それぞれの
  単位の中での相対的な変化だけです
- **合計より構成比**。同じ合計でも、内訳が違えば意味が違います。
  まず3分解と最初の記録の使用率を見る癖をつけると、セッションの
  「どこに払ったか」が読めるようになります
- **「記録なし」は「読まれていない」ではありません**（01 参照）。
  この文書の読み方も、記録に残った範囲の中での話です

## まとめ

- サマリの実測は、合計ではなく構成比で読む
- Copilot では、キャッシュ書込の量と発生ターンが「載せ直し」の
  痕跡を示す。書込は読取よりずっと高い
- Kiro では、最初に記録された文脈使用率が常時文脈の重さの
  目安になり、それがターンごとのクレジットを支配する
- ツールが出すのは実測と構成比まで。構造の読み解きは
  この文書が担い、単価の話はモデルとともに変わるものとして
  ツールの外に置く
